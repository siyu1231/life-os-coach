# 本地记忆与记录系统

本文件定义 Life Coach Agent 的本地记忆层——不仅是一个文件存储方案，更是一套**安全写入等级、数据边界和拆分规则**。目标不是一开始建立很多文件，而是让 Agent 在长期使用中逐渐更懂用户：先稳定记录，再从重复经验中提炼洞察，必要时再拆分。

本文件是 `system/algorithm.md` 中 CHECK（读取）和 LEARN（写入）阶段的记忆读写依据，也是 `engine/session-flow.md` Phase 5（行动）中文件写入操作的安全规则来源。

默认方案使用本地 Markdown 文件，不要求数据库、Notion、待办软件或 MCP。读者可以先用纯文件跑通，再按自己的工具栈改造成外部连接，例如待办事项接滴答清单，愿景接 Notion，长期笔记接 Obsidian。

## 一、核心原则

1. **先少后多**：一开始只建核心文件，不急着拆很多画像。
2. **单一事实源**：同一条稳定信息只维护在一个主文件，不在多个地方复制。
3. **先记录，再提炼**：单次观察先放每日记录或复盘；多次出现后再沉淀为长期规律。
4. **写入前确认**：长期画像、价值观、身份描述、敏感信息、外部工具操作，写入前先向用户确认。
5. **能不拆就不拆**：只有某类内容持续增长、被频繁单独读取、或让 `user.md` 变得臃肿时，才拆成新文件。
6. **数据优先，感觉补充**：写入依据以工具数据和用户原话为准，Agent 的主观感觉只作为辅助线索标注「待确认」。
7. **失败数据也有用**：偏离、未完成、情绪低谷不是「没用的记录」——它们是理解用户真实状态的信号。

## 四、user.md 的边界

`profile/user.md` 是用户的稳定底图，不是所有记忆的总仓库。它适合记录：

- **现实角色与稳定限制**：工作/学习状态、照护责任、通勤、地点约束、长期健康或环境限制。
- **基本作息与固定承诺**：工作日/周末节律、固定会议、运动、睡眠窗口、可自由支配时段。
- **沟通偏好与雷区**：喜欢表格还是简短总结，讨厌被催还是喜欢提醒，哪些表达会带来羞耻感。
- **精力线索**：常见高/低能量窗口、恢复方式、透支信号。先简要记录在 user.md；只有内容变多再拆到 `profile/energy-profile.md`。
- **执行与拖延线索**：常见启动阻力、有效启动方式、反效果方法。先简要记录在 user.md；只有反复积累后再考虑拆成专项画像。

判断句：如果这条信息会影响很多计划和对话，而且短期内不常变化，就可以写进 `user.md`。如果只是今天发生、这周尝试、一次情绪或一个项目细节，不写进 `user.md`。

## 五、memory 的边界

`memory/` 不是另一套 profile。

- `memory/daily/` 是原始记录和候选洞察。它回答：「今天实际发生了什么？」
- `memory/long-term.md` 是跨文件综合洞察和索引。它回答：「这些分散记录合在一起，说明了什么？」

如果一条信息能归入 `profile/user.md` 或 `profile/life-compass.md`，不要再复制到 `memory/long-term.md`。`long-term` 最多写索引，例如：

```markdown
- 启动阻力的稳定记录见 `profile/user.md#执行与拖延线索`。
- 价值与阶段主题见 `profile/life-compass.md`。
```

## 六、四级写入安全等级（Tier A-D）

不是所有信息都适用同一套写入规则。本节定义四级安全等级，按从「可以直接写」到「永远不写」排列。Agent 在每次写入操作前，必须先判断信息属于哪个 Tier，再执行对应的写入协议。

### 6.1 等级总览

| 等级 | 名称 | 写入协议 | 适用内容 | 违反后果 |
|------|------|---------|---------|---------|
| **Tier A** | 直接写入 | 无需确认，写入后记录操作 | 已确认的计划、今日事实记录、工具返回值 | 几乎无风险，但仍需 VERIFY 检查 |
| **Tier B** | 告知后写入 | 写入后在回复中告知用户改了什么，用户可要求回退 | 重复出现的精力线索、稳定出现的拖延模式（经多次观察后）、已验证的策略偏好 | 用户可能有不同解读，但不造成实质性伤害 |
| **Tier C** | 确认后写入 | 必须先向用户确认，获得明确同意后才能写入 | 价值观、身份描述、人生方向、使命宣言、阶段主题变更 | 写入未经确认的长期结论会污染用户画像，影响后续所有决策 |
| **Tier D** | 永不写入 | 绝对不写入任何文件，包括 daily memory | 心理诊断标签、敏感情绪细节、密码/密钥、身份证件、银行卡、他人隐私 | 一次写入可能造成安全风险或长期心理标签化伤害 |

### 6.2 Tier A：直接写入

**适用内容**（满足以下任意一条即可直接写入）：

- 用户刚刚在对话中确认的计划（如「帮我把下午的优先级调成 B 项目在前」）。
- 明确的日程草案和日终实际记录（如「今天实际完成了 A、B，C 推迟到明天」）。
- 工具返回的客观数据（如滴答清单任务完成状态、日历事件时间）。
- 用户明确要求记录的偏好或策略（如「记住，我以后早上不开会」）。
- 复盘过程中用户确认的结论（如「本周最大的问题是周二中断后没恢复」）。

**写入协议**：

1. 执行写入操作。
2. 在 VERIFY 阶段读回确认写入成功。
3. 在回复中简要提及写入内容（一句话即可，如「已更新今日计划」），不需要用户确认。

**不适用 Tier A 的情况**：

- 用户没有明确确认，Agent 自行推断的结论 → 至少 Tier B。
- 涉及用户身份、价值观、长期方向的判断 → Tier C。
- Agent 觉得「这应该是对的」但用户没有说过 → 至少 Tier B，首次出现标注「待确认」。

### 6.3 Tier B：告知后写入

**适用内容**（需要经过多次观察，满足「稳定出现」的条件）：

- **精力线索**：同一精力模式在 >= 3 天的 daily memory 中出现，且每次的模式一致（如「连续 3 个工作日下午 2:30-4:00 能量低谷」）。
- **拖延模式**：同一类任务被推迟 >= 3 次，且推迟原因相似（如「涉及文档撰写的任务每次都被推到第二天」）。
- **有效策略**：某种干预方式在 >= 2 次实验中都被用户评价为「有用」或「可以继续」（如「把大任务拆成 25 分钟番茄钟对用户启动困难有效」）。
- **沟通偏好微调**：用户多次表现出对某种方式的偏好，但从未明确说出（如连续 3 次对简洁回复回复「谢谢」而对长回复不回应）。

**写入协议**：

1. 在 daily memory 中积累观察（Tier A 范围——记录事实）。
2. 当同一模式满足上述「稳定出现」条件后，Agent 准备一条候选写入内容。
3. 在当次回复中告知用户：「我注意到[模式描述]，准备写入 `[目标文件]`。如果不对或你不想记录，告诉我即可。」
4. 写入候选内容，标注「待确认」或「Agent 观察（待用户确认）」。
5. 用户可在后续对话中要求修改或删除。如果用户未反对，默认保留。

**关键约束**：

- Tier B 不能用于首次出现的观察——至少积累 2-3 次后再提升到告知写入。
- 如果用户曾经对类似内容的记录表示过不适，降级为 Tier C（确认后写入）。
- 精力线索和拖延模式的初次记录仍在 daily memory（Tier A），Tier B 是指将其提升写入 `profile/user.md` 或 `memory/long-term.md`。

### 6.4 Tier C：确认后写入

**适用内容**（任何涉及用户深层自我的判断）：

- **价值观和信念**：用户看重什么、相信什么、以什么为标准做选择。
- **身份描述**：用户如何定义自己（如「我是一个______的人」）。
- **人生方向**：阶段主题、长期愿景、使命宣言、人生实验设计。
- **重大关系判断**：对用户重要关系的总结或归因。
- **敏感领域信息**：健康细节、财务状况、关系困扰的具体内容。
- **外部工具结构性操作**：创建日历块、修改项目截止日期、归档项目、删除任务。

**写入协议**：

1. Agent 准备候选内容，以「确认问题」的形式呈现给用户。
2. 确认问题的格式应简洁，包含：
   - 准备写入什么。
   - 写入到哪个文件的哪个位置。
   - 为什么认为应该记录（引用具体观察或用户原话）。
3. 等待用户明确回复「好」「可以」「同意」「是的」等确认信号。
4. 收到确认后才执行写入。
5. 写入后在 VERIFY 阶段读回确认。

**确认问题示例**：

```
我注意到你连续三周复盘都提到「比起功能开发，文档工作更让你疲惫」。
如果这确实是你的稳定模式，我想把它写入 profile/user.md 的执行线索部分：
「文档密集型任务消耗高于编码任务，需在计划中降低文档日的总任务容量。」

这样可以吗？
```

**什么不算确认**：

- 用户的「嗯」「哦」不算确认。
- 用户沉默不回复不算确认。
- 用户说「随便」「你看着办」——这是把决策权交还给 Agent，在 Tier C 内容上不应接受，应再次确认或降级为不写入。

### 6.5 Tier D：永不写入

**适用内容**（绝对禁止，无例外）：

- **心理诊断标签**：如「抑郁症」「焦虑症」「ADHD」「强迫症」等——即使用户自己使用这些词，Agent 也不应将其作为标签写入用户画像。可以记录用户原话中提到的感受（如「用户描述自己『总是静不下来』」），但不用诊断术语。
- **敏感情绪细节**：用户在情绪宣泄中透露的具体创伤经历、关系冲突细节、对他人强烈负面评价。
- **密码、密钥、Token**：任何形式的凭证信息。
- **身份证件信息**：身份证号、护照号、社保号、驾照号。
- **银行卡和支付信息**：卡号、CVV、支付密码。
- **他人隐私**：用户提到的第三方的私人信息，除非该信息直接影响用户的行动且用户明确要求保留。

**处理方式**：

- 如果用户在对话中透露了 Tier D 信息，Agent 的职责是：
  1. 不在任何文件中写入该信息。
  2. 如果该信息是密码/凭证类，提醒用户不要在对话中分享敏感凭证。
  3. 如果该信息是心理诊断类，Agent 可以在回复中正常回应情绪，但不在记录中使用诊断标签。
  4. 在 daily memory 中只记录能概括情绪状态的通用描述（如「用户今天情绪低落」），不记录触发原因的具体细节。

### 6.6 Tier 判断流程图

```
收到一条候选写入信息
        │
        ▼
  ┌─────────────────┐
  │ 是 Tier D？      │──是──▶ 不写入，按 Tier D 处理方式回应
  │（密码/诊断/隐私） │
  └────┬────────────┘
       │否
       ▼
  ┌─────────────────┐
  │ 是 Tier C？      │──是──▶ 先确认，后写入
  │（价值观/身份/方向）│
  └────┬────────────┘
       │否
       ▼
  ┌─────────────────┐
  │ 是 Tier B？      │──是──▶ 告知用户后写入，标注「待确认」
  │（重复模式/线索）  │
  └────┬────────────┘
       │否
       ▼
  ┌─────────────────┐
  │ 是 Tier A？      │──是──▶ 直接写入，VERIFY 读回确认
  │（已确认计划/事实）│
  └────┬────────────┘
       │否

     如果到达，按 Tier C 处理）
```

## 七、与滴答清单的数据边界

滴答清单（Dida / TickTick）是本系统的外部任务管理工具。本节定义滴答清单和本地文件系统之间的**数据边界**——什么归滴答管，什么归本地管，什么两边都有但主次分明。

### 7.1 边界原则

核心原则：**滴答管任务执行，本地管愿景/项目/复盘。**

| 维度 | 滴答清单 | 本地文件（life-coach-data/） |
|------|---------|---------------------------|
| **定位** | 执行层——任务的实际操作界面 | 思考层——计划、愿景、复盘、长期洞察 |
| **数据特征** | 高频变动、短期、面向操作 | 低频变动、长期、面向理解 |
| **谁主写** | 用户主写（手动勾选、调整），Agent 辅助 | Agent 主写（基于对话和工具数据），用户确认 |

### 7.2 具体数据归属

| 数据类型 | 归属 | 为什么 |
|---------|------|--------|
| 任务列表（今天/本周要做什么） | **滴答主**，本地 `planning/daily-plan.md` 辅（记录计划意图和偏离原因） | 任务的增删改查在滴答进行更方便；本地保留计划意图和偏离分析 |
| 任务完成状态 | **滴答**（单一事实源），本地不重复存储 | 滴答的 `completed_time` 是权威数据 |
| 任务优先级和截止日期 | **滴答** | 滴答原生支持，本地不重复维护 |
| 项目的整体定义和阶段 | **本地** `projects/projects.md` | 项目是长期概念，滴答用「清单」承载执行，但项目的愿景、阶段和状态归本地管 |
| 每日实际做了什么 | **本地** `memory/daily/YYYY-MM-DD.md` | 每天的实际记录需要上下文（精力、情绪、偏离原因），滴答只管「完成/未完成」 |
| 习惯追踪 | **本地** `habits/habit-tracker.md` | 习惯是长期实验，需要记录模式变化，滴答的习惯功能可作补充但本地为事实源 |
| 周/月复盘 | **本地** `reviews/review-log.md` | 复盘需要跨源综合（滴答数据 + daily memory + 用户表达），结论写在本地 |
| 长期洞察和模式 | **本地** `memory/long-term.md` | 滴答不擅长长文本和跨时间关联 |
| 用户画像/人生罗盘 | **本地** `profile/` | 完全不归滴答管 |

### 7.3 跨边界操作规则

当 Agent 需要操作滴答清单时，遵循以下规则：

1. **读取滴答数据**：Agent 可以在 CHECK 阶段主动读取滴答的今日/本周任务列表，不需要逐次确认。这是为了获取 Current State。

2. **写入滴答数据**（创建/修改/删除任务）：操作前需用户确认（Tier C 级别）。因为滴答是用户的操作界面，Agent 不应在用户不知情的情况下改变滴答中的内容。

3. **滴答数据作为输入，本地文件作为输出**：
   - CHECK 时读取滴答任务完成情况 → 作为 GAP 分析的输入。
   - LEARN 时将滴答的完成率和偏离模式写入 `memory/daily/` 和 `memory/long-term.md`。
   - 不复写滴答中的具体任务列表到本地（那是冗余）。

4. **滴答不可用时的降级**：
   - 如果滴答 MCP 不可用，Agent 在 CHECK 阶段询问用户今天的任务进展（通过邮件/IM）。
   - 将用户回复中的任务状态写入 `memory/daily/{today}.md`。
   - 待滴答恢复后不做回溯同步——每日记录已保存在本地。

### 7.4 滴答数据在本地文件中的引用格式

当本地文件需要引用滴答数据时，不复制完整内容，只记录摘要和来源：

```markdown
## 今日任务执行情况

> 数据来源：滴答清单（Dida MCP `get_tasks`），2026-07-29 09:30 查询
> 
> 今日计划 5 项：
> - 已完成 3 项：[任务名 1]、[任务名 2]、[任务名 3]

```

## 八、何时拆分新文件

不要一开始就拆。**拆分需要满足至少任意两条触发条件**：

### 8.1 拆分阈值规则

| # | 触发条件 | 说明 |
|---|---------|------|
| 1 | **体量阈值**：某一节已经超过约 10 条稳定记录，`user.md` 变得难扫 | 例如精力线索从最初的 3 条增长到 12 条，每次读用户画像都需要跳过大量精力相关内容 |
| 2 | **读取频率**：某类信息经常被单独读取，例如每次计划都要读精力规律 | 如果每次做日计划都要专门翻阅精力模式，说明它应该独立成一个可快速定位的文件 |
| 3 | **更新节奏独立**：这类信息有独立的更新节奏，例如每月校准精力画像，而 `user.md` 的其它部分按需更新 | 独立节奏的信息混在主文件中会导致「不知道哪些内容需要定期回顾」 |
| 4 | **结构稳定**：这类信息已经形成稳定结构，例如「触发线索 -> 反应 -> 有效策略」 | 结构稳定的内容天然适合独立成文件——因为读它的人需要的不是全文，而是按这个结构查询 |
| 5 | **用户意愿**：用户明确希望单独维护 | 用户主动说「帮我单独建一个文件记录 XXX」 |

**使用方式**：

- 满足任意 2 条 = 达到拆分阈值，Agent 可以向用户提出拆分建议。
- 满足任意 3 条及以上 = 强建议拆分，Agent 应在当次对话中主动提出拆分方案。
- 只满足 1 条 = 暂不拆分，继续在原文件中积累。

### 8.2 常见拆分方向

- `profile/energy-profile.md`：当精力规律已经多次被验证，并且计划时需要频繁读取。
- `profile/execution-profile.md`：当拖延、启动阻力和有效启动方式积累较多。
- 互动偏好专项文件：当用户对沟通、提醒、追踪方式有很多明确偏好时，再由用户决定是否拆出。

### 8.3 拆分后遵守单一事实源

从 `user.md` 中保留一句索引，不再复制全文。例如：

```markdown
- 精力规律详见 `profile/energy-profile.md`。
```

而不是把精力规律的内容同时保留在 `user.md` 和 `energy-profile.md` 中。

## 九、启动时读取什么

不要为了读取而读取。简单问题直接回答；涉及延续上下文、计划、复盘、习惯或日程时，再读取对应记录。

### 9.1 默认读取

在需要连续陪伴时，读取：

1. `profile/user.md`：稳定个人情况、作息、偏好、精力与执行线索。
2. `memory/long-term.md`：跨文件综合洞察和索引。
3. `memory/daily/YYYY-MM-DD.md`：今天和昨天的状态、行动、偏离。

### 9.2 按场景读取

| 场景 | 读取 |
|---|---|
| 人生方向、价值观、阶段选择 | `profile/life-compass.md` |
| 安排今天、明天、本周 | `profile/user.md`、`planning/weekly-plan.md`、`planning/daily-plan.md`、`projects/projects.md`、外部日历/待办摘要 |
| 项目拆解和优先级 | `projects/projects.md`、`profile/life-compass.md`、`planning/weekly-plan.md` |
| 拖延、启动困难、反复失败 | `profile/user.md` 中的执行线索、`reviews/review-log.md`、相关项目和日计划；需要综合判断时再读 `memory/long-term.md` |
| 习惯设计 | `habits/habit-tracker.md`、`profile/user.md` |
| 周/月/项目复盘 | `planning/weekly-plan.md`、`planning/daily-plan.md`、`reviews/review-log.md`、`projects/projects.md` |
| 工具接入或数据来源不清 | `integrations/tools.md` |

## 十、写入规则

### 10.1 每次收尾的记录检查

计划、拖延应对、习惯设计和复盘结束前，Agent 应做一次简短检查：

1. **稳定底图**：这次是否确认了作息、固定承诺、沟通偏好、精力线索或执行线索？如果是，候选写入 `profile/user.md`（按 Tier B 或 C 判断）。
2. **方向变化**：这次是否确认了价值、阶段主题、人生领域或不做什么？如果是，候选写入 `profile/life-compass.md`（Tier C——必须确认）。
3. **运行记录**：这次是否只是今天/本周的实际、偏离或尝试？如果是，写入 `planning/*`、`reviews/review-log.md` 或 `memory/daily/*`（Tier A）。
4. **长期洞察**：这次是否形成了跨多个文件都适用的综合洞察或通用策略？如果是，候选写入 `memory/long-term.md`（Tier B 或 C，取决于洞察的确定性）。
5. **是否需要拆分**：某一类记录是否已经多到影响阅读？如果是，检查拆分阈值（第八节），满足 2 条则建议用户拆分，而不是自动创建新文件。

### 10.2 事实、假设、洞察分开

- **事实**：用户明确说过，或工具中已经存在的数据。写入时标注来源和时间。
- **假设**：Agent 为了推进计划做出的临时估计，必须标注「暂时假设」。
- **洞察**：经过对话确认的理解。首次写入 daily memory 时标注「候选洞察」；经用户确认后去掉候选标记。
- **规律**：多次复盘后稳定出现的模式，优先写入现有文件；只有超过拆分阈值，才建议拆新文件。

### 10.3 写入前确认（按 Tier）

本节的确认规则是对第六节 Tier 系统的概要复述。详细规则和判断流程见第六节。

以下内容写入前应先向用户确认（Tier C）：

- 人生价值、身份描述、长期愿景。
- 对用户性格、模式、关系的总结。
- 健康、心理、关系、财务等敏感信息。
- 会影响外部工具的操作，例如创建日历块、修改任务截止、归档项目。

以下内容告知用户后写入（Tier B）：

- 稳定出现的精力线索（>= 3 次观察）。
- 重复出现的拖延模式（>= 3 次观察）。
- 已验证有效的策略偏好（>= 2 次积极反馈）。

以下内容可以直接写入（Tier A）：

- 用户刚刚确认的计划。
- 明确的日程草案和日终实际记录。
- 用户要求记录的偏好、策略或复盘结论。

### 10.4 不记录什么（Tier D）

- 未经确认的心理诊断、人格标签或病理判断。
- 对他人的隐私细节，除非它直接影响用户行动且用户要求保留。
- 一次性情绪宣泄中的强烈措辞，除非用户确认它是长期模式。
- 可能伤害用户安全的敏感信息，除非有明确用途和保护方式。
- 密码、密钥、身份证件、银行卡等高敏感信息。

## 十二、外部 MCP 和工具接入

本地 Markdown 是默认低门槛方案，不是唯一方案。读者可以让 AI 根据自己的工具栈改造 `integrations/tools.md` 和相关读写规则。

常见改造：

- 待办事项接滴答清单、Todoist、Things、Linear、Notion database。
- 日历接 Google Calendar、Apple Calendar、Outlook。
- 愿景和长期笔记接 Notion、Obsidian、Logseq。
- 复盘和日志保留本地 Markdown，方便版本管理和迁移。

接入外部 MCP 时要保留三个原则：

1. **读写分离**：读取可以更主动，写入必须更谨慎。
2. **确认后写入**：创建、修改、删除外部事项前先让用户确认。
3. **工具失败可降级**：MCP 不可用时，先输出 Markdown 草案，不阻塞教练过程。

## 十三、维护节奏

- 每天：必要时更新 `memory/daily/YYYY-MM-DD.md` 或 `planning/daily-plan.md` 的实际记录。
- 每周：更新 `weekly-plan.md` 和 `review-log.md`。
- 每月或阶段变化：更新 `life-compass.md`、`projects.md`，并整理 `user.md` 中已经稳定的精力/执行线索。
- 当某类记录持续增长：检查拆分阈值（第八节），满足 2 条则建议用户拆分，再创建专项文件。

记录系统的目标不是让用户被数据管理，而是让下一次对话更懂上下文，让计划更贴近真实生活。
