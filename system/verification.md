# 三级验证系统

本文件定义 Life Coach Agent 的验证框架——**数据验证、证据验证、觉察验证**三级体系。验证的目标不是追求完美，而是确保「做完了」不是一个模糊的感觉，而是一个可以事后检查的事实。

本文件是 `system/algorithm.md` 中 VERIFY 阶段的详细方法论来源。它继承了 algorithm 的核心原则——「没有证据 = 没做完」、「声明只凭工具证据关闭」、「每个声明附带可证伪条件」——并将其转化为可操作的验证流程。

## 一、验证哲学

### 1.1 为什么需要验证

在 Life Coach Agent 的运行环境中，「我做完了」这句话有三个可能的说话者，每个都有不同的可靠性：

| 说话者 | 可靠性 | 风险 |
|--------|--------|------|
| **工具返回值** | 高（可重复验证） | 工具可能返回成功但实际未生效（罕见但存在） |
| **用户的自我报告** | 中等（诚实但可能不准确） | 用户可能记得不准确、标准不清晰、或习惯性低估/高估 |
| **Agent 的推断** | 低（基于模式，非事实） | Agent 可能把「像做完了」当成「做完了」 |

验证的核心目的：**把「做完了」的判断依据从最不可靠的层级推高到最可靠的层级。**

### 1.2 验证原则

1. **数据优先，感觉补充**：先看能不能用工具数据验证。数据验证通过后，再用证据和觉察做补充确认。不能反着来——不能先凭感觉说「应该做完了」，再去找数据佐证。
2. **验证失败不是惩罚**：验证未通过不意味着「做错了」或「失败了」——它意味着「完成状态还不明确，需要进一步确认」。验证是一个信息收集过程，不是一个审判过程。
3. **能验证多少就验证多少**：不是所有操作都能通过三级验证全部覆盖。简单操作可能只需要一级（文件写入→读回），复杂操作才需要三级。不要为了凑三级而创造不必要的验证步骤。
4. **验证结果要记录**：不管通过还是未通过，验证结果都应写入 `memory/daily/` 或对应的执行记录中。未通过的验证是后续 GAP 分析的重要信号。

## 二、三级验证总览

| 级别 | 名称 | 核心问题 | 验证对象 | 验证方式 | 可靠性 | 适用场景 |
|------|------|---------|---------|---------|--------|---------|
| **L1** | 数据验证 | 数字对不对？文件在不在？时间戳对不对？ | 工具返回值、文件系统、API 状态码、数据字段 | 交叉比对、读回确认、数值校验 | 高（客观） | 一切有工具返回值的操作 |
| **L2** | 证据验证 | 有没有具体事实支持「完成了」？ | 具体产出物、邮件回复内容、文件实际内容、截图 | 内容存在性检查、关键特征匹配 | 中高（客观内容，但判断可能有主观成分） | 需要产出物的操作 |
| **L3** | 觉察验证 | 用户的表达是否确认了状态？ | 用户原话、情绪表达、自我评估 | 原话引用、确认信号识别 | 中（依赖用户诚实度和标准清晰度） | 需要用户主观判断的操作 |

### 2.1 三级之间的关系

```
L1 数据验证（必须）
    │
    ├── 通过 ──▶ L2 证据验证（按需）
    │               │
    │               ├── 通过 ──▶ L3 觉察验证（按需）
    │               │               │
    │               │               ├── 通过 ──▶ VERIFIED ✅
    │               │               └── 未通过 ──▶ 标注「用户感知不一致」
    │               │
    │               └── 未通过 ──▶ PARTIALLY_VERIFIED ⚠️
    │
    └── 未通过 ──▶ UNVERIFIED ❌（重试或人工核对）
```

L1 是必须的——只要操作涉及工具调用，就必须做数据验证。L2 和 L3 按需进行：如果操作本身不需要用户确认（如纯文件写入），L2 的读回确认就足够了，不需要 L3。如果操作涉及主观判断（如「整理本周复盘」），则需要 L3 的用户确认。

## 三、第一级：数据验证（L1）

### 3.1 定义

数据验证是**最基础、最客观**的验证层级。它回答：「工具返回的数据和我们期望的一致吗？」

### 3.2 验证内容

| 数据类型 | 验证什么 | 怎么验证 |
|---------|---------|---------|
| **文件写入** | 内容是否真的写入了？ | 读取目标文件，检查对应行/字段是否存在 |
| **文件修改** | 修改的内容是否和预期一致？ | 读取文件变更前后的关键字段，对比差异 |
| **API 调用返回值** | 返回值表示成功还是失败？ | 检查 `errcode`、`status`、`message_id` 等状态字段 |
| **滴答清单任务状态** | 任务的 `completed_time`、`status` 是否已更新？ | 调用滴答查询 API，核对任务字段 |
| **邮件发送** | 邮件是否发送成功？ | 检查 API 返回的 `errcode == 0` 且 `message_id` 非空 |
| **邮件获取** | 获取到的邮件是否是新的？ | 检查 `mailid` 不在去重集合中 |
| **时间戳** | 操作的实际时间是否合理？ | 对比操作时间戳和当前时间，偏差不超过合理范围 |
| **计数/统计** | 数量是否符合预期？ | 文件数量、任务完成数、天数等数值直接比较 |
| **日历事件** | 事件是否真的创建/更新了？ | 调用日历查询 API，确认事件的标题、时间与写入一致 |

### 3.3 文件写入验证（L1 的核心应用）

文件写入是 Agent 最频繁的操作。文件写入验证的流程如下：

```
写入文件
    │
    ▼
读回同一文件（不是相信写入工具的返回值）
    │
    ▼
检查目标内容是否出现在读回的内容中
    │
    ├── 是 ──▶ L1 通过
    └── 否 ──▶ L1 未通过，记录差异，重试写入一次
```

**示例**：

```bash
# 写入 memory/daily/2026-07-29.md
# 验证：读取同一个文件
grep "下午启动实验" life-coach-data/memory/daily/2026-07-29.md
# 预期：有输出，内容包含我们写入的那条记录
```

### 3.4 API 返回值验证（L1 的核心应用）

```python
# 伪代码示例
result = send_email(to=user, subject="早安", body="...")

# L1 数据验证
assert result.errcode == 0, f"发送失败: errcode={result.errcode}"
assert result.message_id is not None and result.message_id != "", "message_id 为空"
# 通过 → L2（如果需要检查邮件内容是否正确）
```

## 四、第二级：证据验证（L2）

### 4.1 定义

证据验证回答：「有没有具体事实可以证明『做完了』？」L2 不是验证工具返回值（那是 L1），而是验证**操作的实际效果是否体现在产出物中**。

### 4.2 L2 vs L1 的区别

| 维度 | L1 数据验证 | L2 证据验证 |
|------|-----------|-----------|
| **验证对象** | 工具返回值是否正确 | 实际效果是否达到预期 |
| **典型操作** | 文件写入后读回 | 检查读回的文件内容是否完整、是否有缺失字段 |
| **问题** | 「文件存在吗？」 | 「文件内容符合要求吗？」 |

### 4.3 验证内容

| 证据类型 | 验证什么 | 怎么验证 |
|---------|---------|---------|
| **文件内容完整性** | 写进去的内容是否完整，有没有截断或缺失？ | 读取文件后，对比写入的关键字段数量和内容 |
| **邮件内容正确性** | 发出的邮件主题、收件人、正文是否正确？ | 发送后读取已发送邮件的内容，对比发送时的参数 |
| **用户回复中的证据** | 用户回复的内容是否包含我们期望确认的信息？ | 提取用户回复中的关键陈述，和我们的问题对照 |
| **产出物存在性** | 说有产出物（如复盘记录、项目计划），产出物真的在吗？ | 检查目标文件是否有对应的新增内容，不只看「文件存在」 |
| **状态变更的实际效果** | 修改了某个状态后，依赖该状态的其他地方是否一致？ | 交叉检查关联文件，确保一致性 |

### 4.4 证据验证示例

**场景：Agent 帮用户整理本周复盘**

```
L1 数据验证（通过）：
  - review-log.md 文件存在，大小增加
  - grep "W30" review-log.md 有 5 条匹配

L2 证据验证（需要检查）：
  - 每条复盘条目是否包含「偏离模式」「可能原因」「下次实验方向」三个字段？
  - 本周 5 个工作日是否都已覆盖（不是 4 天或 6 天）？
  - memory/long-term.md 中是否新增了 W30 复盘的关键洞察索引？
```

## 五、第三级：觉察验证（L3）

### 5.1 定义

觉察验证回答：「用户自己的表达是否确认了某个状态？」这是最主观、但也是唯一能验证「用户是否真心觉得做完了」的层级。

### 5.2 什么时候需要 L3

L3 不是所有操作都需要。只有在以下情况才触发 L3：

1. **需要用户主观判断**：完成标准包含「用户觉得可以了」「用户满意」这类主观条件。
2. **涉及用户长期画像或价值观**：写入 `profile/user.md` 或 `profile/life-compass.md` 的内容，数据验证无法判断「这真的符合用户吗」。
3. **用户之前说过「感觉不对」**：同一类任务之前用户对结果有疑虑，这次需要直接确认。
4. **情绪状态类操作**：如「今天你感觉怎么样？」——用户的自我报告是唯一的数据源。

### 5.3 验证内容

| 觉察来源 | 验证什么 | 怎么验证 |
|---------|---------|---------|
| **用户原话** | 用户是否明确表达了完成或满意？ | 在记录中引用用户原话，标注引用位置（邮件/IM 消息 ID） |
| **确认信号** | 用户是否给出了明确的确认信号？ | 检查「好」「可以」「是的」「对的」「就是这样」等明确确认词 |
| **情绪一致性** | 用户的表达和任务的完成状态是否一致？ | 如果用户说「做完了」但语气犹豫/消沉，标记「待确认」 |
| **偏差感知** | 用户自己的感知和数据之间有差距吗？ | 对比用户自述和数据验证结果，如有差距标注「感知偏差」 |

### 5.4 L3 验证的引用格式

在 daily memory 中记录 L3 验证结果时，使用以下格式：

```markdown
## 觉察验证记录

- **验证对象**：W30 复盘结论「下午能量低谷可能与午餐类型相关」
- **验证方式**：用户确认
- **用户原话**：「对，这个观察很准。我确实发现吃面条的下午特别困，吃沙拉会好很多。」
- **来源**：邮件回复，mailid=xxx，2026-07-29 15:22
- **验证结果**：L3 通过 ✅
```

### 5.5 「确认信号」的判断标准

| 用户表达 | 算不算确认 | 说明 |
|---------|-----------|------|
| 「好」「可以」「是的」「对」「没错」 | **算确认** | 明确的肯定 |
| 「就这样吧」「差不多」「还行」 | **算弱确认**（标注「用户接受但热情不高」） | 可能意味着用户不同意但不想继续讨论，需关注后续表现 |
| 「嗯」「哦」 | **不算确认** | 可能是敷衍或还在思考 |
| 沉默不回复 | **不算确认** | Agent 不应假设沉默 = 同意 |
| 「随便」「你看着办」 | **不算确认**（Tier C 内容上应再次确认） | 用户把决策权交还给 Agent |

## 六、验证流程

### 6.1 标准验证流程

```
操作执行完毕
    │
    ▼
┌─────────────────────────────────────────────┐
│  L1 数据验证（必须）                          │
│  工具返回值检查 / 文件读回 / 状态码检查        │
└────┬────────────────────────────────────────┘
     │
     ├── L1 未通过 ──▶ 重试一次
     │                   │
     │                   ├── 二次通过 ──▶ 继续
     │                   └── 二次失败 ──▶ UNVERIFIED，标记 NEEDS_HUMAN_ATTENTION
     │
     └── L1 通过
           │
           ▼
     ┌─────────────────────────────────────────────┐
     │  是否需要 L2（证据验证）？                    │
     │  判断标准：操作是否有实际产出物需要检查？       │
     └────┬────────────────────────────────────────┘
          │
          ├── 不需要 ──▶ L1 通过即可，进入记录
          │
          └── 需要
                │
                ▼
          ┌─────────────────────────────────────────────┐
          │  L2 证据验证                                │
          │  内容完整性 / 产出物检查 / 关联一致性         │
          └────┬────────────────────────────────────────┘
               │
               ├── L2 未通过 ──▶ PARTIALLY_VERIFIED，列出缺失项
               │
               └── L2 通过
                     │
                     ▼
               ┌─────────────────────────────────────────────┐
               │  是否需要 L3（觉察验证）？                    │
               │  判断标准：是否需要用户主观确认？              │
               └────┬────────────────────────────────────────┘
                    │
                    ├── 不需要 ──▶ VERIFIED ✅
                    │
                    └── 需要
                          │
                          ▼
                    ┌─────────────────────────────────────────────┐
                    │  L3 觉察验证                               │
                    │  用户原话引用 / 确认信号检查 / 情绪一致性    │
                    └────┬────────────────────────────────────────┘
                         │
                         ├── L3 未通过 ──▶ VERIFIED（数据通过）但标注「用户感知不一致」
                         │
                         └── L3 通过 ──▶ VERIFIED ✅
```

### 6.2 验证记录格式

每次验证完成后，在 `memory/daily/{today}.md` 中追加验证记录：

```markdown
### 验证记录：{操作名称}

- **时间**：2026-07-29 15:30
- **操作**：更新 daily-plan.md 的下午优先级
- **L1 数据验证**：✅ 文件读回确认，`planning/daily-plan.md` 的 ## 下午 区块第一条已改为「B 项目接口文档」
- **L2 证据验证**：✅ 不需要（单文件修改，L1 的读回即覆盖了内容正确性）
- **L3 觉察验证**：✅ 用户回复「好的，谢谢」确认了修改
- **最终结果**：VERIFIED
```

## 七、场景示例

### 7.1 滴答场景：验证任务完成状态

**操作**：用户说「今天的 A 任务做完了」，Agent 在滴答中标记任务完成。

**验证流程**：

```
1. Agent 调用滴答 `complete_task` API 标记任务完成。

2. L1 数据验证：
   - 调用滴答 `get_task` API 查询同一任务。
   - 检查返回的 `completed_time` 不为空。
   - 检查 `status` 字段为 `completed`（滴答状态值 = 2）。
   → 通过：`completed_time = "2026-07-29T14:30:00+08:00"`, `status = 2`

3. L2 证据验证（不需要——滴答任务完成状态本身没有额外产出物）：
   → 跳过

4. L3 觉察验证（按需）：
   - 用户说「做完了」，Agent 可附加检查：滴答中的 `completed_time`（14:30）是否与用户说的「刚做完」（14:28）大致吻合。
   - 如果用户说「做完了」但滴答显示该任务的上次修改时间还是 3 天前 → 可能用户指的是另一个任务，或者滴答没同步。
   → 通过：时间吻合，用户确认和工具数据一致。

5. 结果：VERIFIED ✅
```

**关键点**：
- 滴答任务完成的权威数据源是滴答 API 返回值（L1），不是用户的话（L3）。
- 用户的话和滴答数据一致时，验证最可靠。
- 用户的话和滴答数据不一致时 → 优先相信滴答数据，然后和用户核对（而不是反过来）。

### 7.2 邮件场景：验证邮件发送和用户回复

**操作**：Agent 发送早安问候邮件，并收到了用户的回复。

**验证流程（发送端）**：

```
1. Agent 调用邮件发送 API。

2. L1 数据验证：
   - 检查 API 返回值：errcode == 0，message_id 非空。
   → 通过：errcode=0, message_id="msg_abc123"

3. L2 证据验证：
   - 调用 `get_mail_content` API 读取刚发送的邮件内容。
   - 检查：subject 正确、收件人正确、正文未被截断。
   → 通过：内容与发送时参数一致
```

**验证流程（接收端）**：

```
1. Agent 调用邮件获取 API 拉取新邮件。

2. L1 数据验证：
   - 检查 mailid 不在去重集合（processed_mailids）中。
   - 检查 `send_time` 在我们上次拉取之后。
   → 通过：新邮件，mailid="mail_xyz789"

3. L2 证据验证：
   - 提取邮件纯文本内容。
   - 检查内容非空、可读。
   - 如果用户回复中提到了具体任务名或状态词（如「完成了」「推迟了」），确认这些词出现在内容中。
   → 通过：内容为「今天上午把 B 项目的接口文档写完了，下午想推进 A 项目的……」

4. L3 觉察验证（按需——如果用户有情绪表达）：
   - 用户说「写完了，但感觉写得不太好」。
   - Agent 在 daily memory 中记录 L3 验证：
     - 任务完成状态：数据验证通过（滴答 completed_time 存在）
     - 用户主观感受：「写得不太好」（用户原话，mailid=mail_xyz789）
     - 结论：任务已客观完成，但用户主观满意度低 → 标注「待复盘」
   → 通过，但标注了「主观满意度低」
```

### 7.3 Coach 场景：验证「整理本周复盘」

**操作**：用户说「帮我把这周的复盘整理一下」，Agent 执行复盘整理。此任务有 ISA 文档定义了 4 条 Claims。

**验证流程**：

```
ISA Claims：
  Claim 1: 本周 5 个工作日的 daily memory 关键记录已合并到 review-log.md
  Claim 2: 至少识别出 2 个重复出现的偏离模式
  Claim 3: 每个偏离模式附带了可能原因和下次实验方向
  Claim 4: 复盘结论中最重要的一条已写入 memory/long-term.md

验证：

1. L1 数据验证：
```

## 八、「以为做完了」的常见陷阱

以下是在实际运行中最常见的「以为做完了但实际没做完」的场景。Agent 在 VERIFY 阶段应逐项检查这些陷阱。

### 8.1 不检查文件——「我写了啊」

**陷阱**：Agent 调用了文件写入工具，工具显示成功，Agent 就认为「写好了」。但实际上文件可能因为路径错误、权限问题、或写入工具有 bug 而实际未写入。

**真实场景**：
- Agent 把内容写到了 `life-coach-data/memory/daily/2026-07-29.md`，但实际上目录 `memory/daily/` 不存在，写入工具静默失败。
- Agent 用相对路径写了文件，但当前工作目录不是预期的，文件写到了错误的位置。

**正确的 VERIFY**：
- 写入后**立即读取**同一个文件，不是相信写入工具的返回值。
- 用绝对路径读取，不是假设文件在某个位置。
- 在 `grep` 中查找写入的具体内容，不是只看文件存在。

### 8.2 不确认邮件发送——「我发了啊」

**陷阱**：Agent 调用了邮件发送 API，然后直接告诉用户「已发送」。但实际上 API 调用可能超时、被限流、或返回了非零 errcode。

**真实场景**：
- 企微邮件 API 返回 `errcode=45009`（接口调用超过限制），Agent 没有检查 errcode 就认为发送成功。
- API 调用因网络问题超时，发送实际未执行，Agent 没有重试机制。

**正确的 VERIFY**：
- 必须检查 `errcode == 0`。
- 必须检查 `message_id` 非空。
- 如果 API 调用失败，至少重试一次。
- 二次失败后，降级处理：记录失败，不假装发送成功。
- **不要发送「确认发送成功」的确认邮件**——如果第一封邮件可能失败，就没有理由相信确认邮件能成功，而且这会形成无限循环。

### 8.3 凭感觉判断——「应该做完了」

**陷阱**：Agent 根据上下文推断某件事「应该已经做完了」，然后按「已完成」处理。例如：

- 用户昨天的 daily memory 为空，Agent 推断「昨天可能没什么特别的事，跳过即可」。
- 用户在之前的邮件中提到了某个任务，Agent 推断「既然没再说起，应该是完成了」。
- Agent 根据用户长期模式推断「这个用户一般下午效率低，今天大概也是」——而不是去查今天的实际数据。

**真实场景**：
- 用户连续 3 天没有回复早安邮件，Agent 推断「用户忙，不需要调整频率」——但实际上用户在等待回复。
- 用户说「我下午想把那件事做掉」，Agent 推断「那件事」指的是之前邮件中提过的 A 项目——但实际上用户指的是另一个紧急的事。

**正确的 VERIFY**：
- 任何涉及用户状态的判断，如果可以通过工具数据验证，就必须验证。
- 如果无法通过工具数据验证（如用户没有启用滴答），标注「基于推断，待用户确认」。
- **推断不能替代验证**。推断是 CHECK 阶段的输入，不是 VERIFY 阶段的输出。

### 8.4 不对比数据——「看起来差不多」

**陷阱**：Agent 修改了某个文件，然后看了一眼文件，觉得「差不多」，就标记完成。但实际上修改的内容可能不完整、格式错乱、或缺失关键字段。

**真实场景**：
- Agent 更新 `planning/daily-plan.md` 的下午优先级，但没有检查修改后的任务顺序是否正确——可能把 A 项目的子任务放在了 B 项目之前，但用户说的「优先 B 项目」是指 B 项目的所有子任务都要在 A 之前。

**正确的 VERIFY**：
- 修改后读回文件时，不只检查文件存在，要检查**修改后的具体内容**是否符合用户的要求。
- 如果是修改结构（如排序、归类），检查每条记录的实际位置。
- 如果用户的要求有歧义（如「优先 B 项目」是指整个项目还是项目的主任务），在修改前就先澄清，而不是修改后再发现不对。

### 8.5 忽略用户纠正——「用户说了但我觉得不对」

**陷阱**：用户说「这个不对」，Agent 把用户的纠正当成「用户可能记错了」而不是「我需要调整」。例如：

- 用户说「我下午其实做了 X，不是 Y」，Agent 在 daily memory 中仍写 Y，因为滴答显示的是 Y。
- 用户说「这个归因不准确」，Agent 仍然保留原归因。

**正确的处理**：
- 如果用户的自我报告和工具数据冲突，**以工具数据为准**（数据优先原则），但必须标注冲突并询问用户。
- 在 daily memory 中同时记录工具数据和用户自我报告，标注「数据不一致，待确认」。
- 如果用户确认自己的报告是正确的（「滴答上我忘记录了」），以用户确认为准但保留工具数据的原始记录作为上下文。

### 8.6 忽略步骤——「跳一步没关系」

**陷阱**：在简单的操作中跳过 VERIFY 步骤，因为「太简单了，不可能会出错」。

**真实场景**：
- 「只是在 daily memory 里加一行记录」→ 跳过 VERIFY → 其实加到了错误日期的文件中。
- 「只是更新一个滴答状态」→ 跳过 VERIFY → 其实更新了错误的任务（ID 相似）。

**正确的处理**：
- **简单不等于可以跳过**。简单操作出错概率低，但出错后的发现成本高（因为没人会觉得这里会出错）。
- 对于高频操作（如 daily memory 追加），至少做最小验证：grep 一下刚写入的关键词。
- 对于单次操作（如更新滴答状态），验证的成本很低（一次 API 查询），但跳过的风险很高。

### 8.7 陷阱检查清单

Agent 在每次 VERIFY 阶段开始前，应快速过一遍这个清单：

```
□ 1. 我检查了每次文件写入的实际内容吗（不只相信工具返回值）？
□ 2. 我检查了每次 API 调用的 errcode / status 吗？
□ 3. 我有没有用推断替代了验证（「应该没问题」）？
□ 4. 我有没有对比数据（不只看了文件存在）？
□ 5. 用户的纠正有没有被记录而不是忽略？
□ 6. 我有没有因为「太简单」跳过验证步骤？
□ 7. 所有「做完了」的声明都附带验证方式了吗？
```

## 九、验证失败的处理

### 9.1 验证结果分级

| 结果 | 含义 | 处理方式 |
|------|------|---------|
| `VERIFIED` | L1 通过（+ L2/L3 按需通过） | 正常记录，关闭对应 ISA Claim（如有） |
| `PARTIALLY_VERIFIED` | L1 通过但 L2/L3 部分未通过 | 记录通过和未通过的项目，分析未通过的原因。如果未通过的是关键项，重试或标记 NEEDS_HUMAN_ATTENTION |
| `UNVERIFIED` | L1 未通过 | 重试一次。二次失败后标记 NEEDS_HUMAN_ATTENTION，在 memory 中记录失败原因 |
| `DATA_CONFLICT` | L1 通过但 L3（用户感知）与数据不一致 | 以数据为准，同时记录冲突并询问用户 |

### 9.2 重试策略

- 文件写入失败：重试一次。二次失败后先输出 Markdown 草案（`memory/daily/{today}-draft.md`），不阻塞整个过程。
- API 调用失败（网络错误/超时）：重试一次（间隔 2 秒）。二次失败后降级处理。
- API 调用失败（业务错误如 errcode 非 0）：不重试。记录 errcode 和错误信息，分析原因。
- 滴答不可用：降级到本地文件方案（见 `system/memory-system.md` 第七节）。

### 9.3 标记 NEEDS_HUMAN_ATTENTION

当验证多次失败且无法自动修复时，在 `memory/daily/{today}.md` 中追加：

```markdown
### NEEDS_HUMAN_ATTENTION

- **时间**：2026-07-29 15:45
- **操作**：更新滴答清单任务 #1234 状态为「完成」
- **失败原因**：滴答 MCP `complete_task` API 返回 `errcode=500`（服务器内部错误），重试 1 次后仍失败
- **影响**：该任务在本次循环中无法标记为完成
- **建议**：请手动在滴答中标记该任务完成
```
