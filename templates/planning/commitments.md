# 承诺追踪

> 本文件记录用户提到的**未来承诺和意图**——不计入日常任务，但需要在特定日期被 Cron 系统主动提醒。它不是日常计划，而是「到时候别忘了这件事」的跨天保险。

## 为什么需要这个文件

日常计划 (`daily-plan.md`) 只记录当天的安排。但用户经常在对话中提到未来要做的事：

- 「我打算下个月开始备考」
- 「周末想去看电影，要先买票」
- 「下周五约了朋友吃饭」
- 「两周后开始跑步」

如果这些承诺只记录在 `memory/daily/` 中，Cron 系统不会主动检查和提醒它们——Agent 可能在上周聊过「考公」，但本周没有在读 `daily/` 时命中正确的日期。

本文件将这些承诺从「被遗忘在 daily 里」提升为「Cron 系统主动检查的数据源」。

## 文件格式

### 待办承诺（活跃的）

| # | 承诺 | 目标日期/时间 | 来源对话 | 前置检查 | 提醒时间 | 状态 |
|---|------|-------------|---------|---------|---------|------|
| 1 |  | YYYY-MM-DD | 对话/邮件 | 需要在此日期前做什么？ | 提前提醒的 Cron 节点 | pending / done / cancelled |

**字段说明：**

- **承诺**：用户說的具体承诺，尽量引用原话。
- **目标日期/时间**：承诺执行的日期。如果用户说的是「下个月」，写具体日期（先估一个，下次确认）。
- **来源对话**：这条承诺是在哪次对话中产生的（`daily/YYYY-MM-DD.md` 或 `long-term.md` 的记录 ID）。
- **前置检查**：到目标日期之前需要做什么？例如「周末看电影」→ 先买票；「下周考公报名」→ 确认报名材料。
- **提醒时间**：Agent 应该在什么 Cron 节点检查这条路？例如 `morning`（晨间）、`night_review`（晚间）、`all`（全天任何节点）。
- **状态**：`pending` = 等待中；`done` = 已完成；`cancelled` = 用户取消了。

## Agent 如何操作本文件

### CHECK 阶段（每个 Cron 节点触发时）

```
1. 读取本文件
2. 筛选：状态为 pending、提醒时间匹配当前 Cron 槽位、目标日期 <= 今天
3. 将匹配的承诺注入 Current State 摘要的「待提醒承诺」部分
4. 如果目标日期 = 今天，且该承诺有关联的前置检查（如买票），在触达邮件中轻量提到
```

### ACT 阶段（用户表达了新的未来意图时）

```
1. 如果用户在对话中表达了未来意图：
   - "我打算 ___（时间）___"
   - "我想在 ___ 做 ___"
   - "周末要 ___"
   - "下个月开始 ___"
   → 在对话中确认关键字段（具体日期、前置动作），写入本文件

2. 写入协议：
   - 暂不写入本文件 → 先记录到 dialogue session 中的 memory
   - 在 Phase 6（闭环）时检查本次对话中是否有未写入的未来意图
   - 对话框中已经确认的未来意图 → 直接追加到本文件（Tier A 直接写入）
   - 对话框中未确认的未来意图 → 标记为 pending_confirmation，下一轮对话中确认
```

### LEARN 阶段（承诺完成或过期时）

```
1. 用户完成了一条 pending 承诺 → 移到「已完成/取消」，记录结果
2. 用户取消了一条 pending 承诺 → 移到「已完成/取消」，标记为 cancelled
3. 目标日期已过但未完成 → 在下次 Cron 触达时轻量询问：是延期还是取消？
```

| 1 | 「周末要去看《哪吒》」 | 2026-08-02（周日） | daily/2026-07-30.md | 提醒买票（周三前） | morning | pending |
| 2 | 「下个月开始备考公务员」 | 2026-09-01 | daily/2026-07-28.md | 确认报名时间、准备资料 | morning | pending |
