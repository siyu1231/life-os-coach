# 休息日调度重设计

## 概述

将休息日从「不做任务、不打搅」的纯休息模式，重设计为**用户可驾驭的多档节奏**：
默认可以推进长期目标（副业、兴趣、自我提升），用户主动声明则切为纯休息模式。

## 动机

当前设计假定：周末/节假日 = 用户不想工作。现实更复杂：

- 很多人在周末推进副业、兴趣项目、深度学习
- 但也有周末需要完全放空的时候（旅游、家庭日）
- 即使是纯休息，日程事件（高铁、航班、约会）也需照常提醒
- 当前 3 节点轻量问候缺少数据驱动——泛泛问「想干嘛」而不是基于用户已有的承诺主动提醒

## 三模式对比

| | 工作日模式 | 休息日默认模式 | 纯休息模式 |
|---|---|---|---|
| 触发条件 | 周一-周五（含调休补班） | 周末/节假日，无 `rest_day` 声明 | 用户声明了某天为 `rest_day` |
| Cron 节点 | 7 个（09:30/10:30/14:30/15:30/16:30/17:30/22:30） | 4 个（10:00/14:30/17:30/22:30） | 4 个（10:00/14:30/17:30/22:30） |
| 任务提醒 | 对照日计划追踪进度 | 基于长期目标 + 承诺主动提醒，可协商 | 不追任务 |
| 日程事件提醒 | 有 | 有 | 有 |
| 体验记录 | 有 | 有 | 有 |
| 消息风格 | warm/brief/challenge 可切换 | 轻松提醒，用户说不做就调整 | 纯陪伴，不推进任何工作 |

## 日类型判断逻辑

`getDayType()`（API 查询）和 `commitments.md` 中的用户声明分开判断：

```
日历类型（API 查询 → timor.tech → mxnzp.com → 本地推算）：
  workday   — 普通工作日
  weekend   — 周末
  holiday   — 法定节假日
  makeup    — 调休补班日（行为同 workday）
  unknown   — API 异常降级（行为同 workday）

用户声明（从 commitments.md 读取）：
  rest_day  — 用户声明某日为纯休息日

最终 Cron 模式 = 日历类型 × 用户声明：

  日历 workday + 无声明     → 工作模式
  日历 workday + rest_day   → 纯休息模式（请假场景）
  日历 weekend + 无声明     → 休息日默认模式
  日历 weekend + rest_day   → 纯休息模式
  日历 holiday + 无声明     → 休息日默认模式
  日历 holiday + rest_day   → 纯休息模式
```

关键变化：

1. **周末/节假日默认不再纯休息** ——改为休息日默认模式（可工作）
2. **用户声明 `rest_day` 可覆盖任何日历类型** ——工作日请年假也能切纯休息

## 休息日默认模式 Cron 节点

休息日节点从 3 增加到 4，去掉了工作日的高频番茄钟检查（10:30/15:30/16:30），保留有意义的里程碑：

### 10:00 — 晨间启动

```
回顾：
  - 读取昨日 memory/daily/{yesterday}.md
  - 读取 planning/commitments.md，筛选今日到期或标记「每日」的 step
  - 读取长期目标中在未来 7 天内到期的里程碑

开启：
  - 早安问候（比工作日晚，用户可能睡懒觉）
  - 主动列出今日相关承诺和长期目标拆解：
    「早上好。今天有你之前提到的 __（承诺），
      还有一个从 __（长期目标）拆出来的 __。
      有想推进的吗？不想做也没关系，告诉我一声我就调整。」

若用户回复「不想做」 → 记录跳过，调整后续提醒
若用户回复「只做 __」 → 聚焦该项，其余不追问
若用户未回复 → 14:30 节点轻量跟进
```

### 14:30 — 午后跟进

```
回顾：
  - 检查上午是否有用户回复或执行记录
  - 读取 10:00 列出的事项

开启：
  - 若用户已推进 → 肯定 + 问下午计划
    「上午把 __ 搞定了，不错。下午还想做什么吗？」
  - 若用户未回复 → 轻量提醒（不催促）
    「刚才提到的 __ 还想做吗？不想做的话告诉我一声就好～」
  - 若用户上午已说不做 → 记录调整为纯休息，不再追问任务
```

### 17:30 — 日终收尾

```
回顾：
  - 今日承诺执行情况（哪些做了/哪些跳过/哪些被用户取消）
  - 全天感受线索

开启：
  - 未完成项处置：延期/取消/明天
  - 若次日为工作日 → 轻量衔接：「明天是工作日了，今天的 __ 要延到明天吗？」
  - 若次日为休息日 → 极简：「今天有什么收获吗？哪怕是很小的。」
  - 若长期目标拆解的 step 今日未推进 → 询问是否重新排期
```

### 22:30 — 晚间复盘

```
与工作日共享同一节点，内容根据当日模式切换：

休息日默认版：
  - 回顾今日感受 + 执行亮点
  - 次日预览：
    - 若次日为工作日 → 提示查看日程和待办
    - 若次日为休息日 → 极简回顾
  - 轻量提示未来一周的承诺概览
```

## 纯休息模式

### 触发方式

用户在对话/邮件中表达某天全天的外出/旅游/休息意图时，Agent 自动识别并写入 `commitments.md`：

示例用户消息：
- 「周六去南京旅游」
- 「下周三请假，全天在医院」
- 「周日想完全放空，什么都不做」

Agent 在 session-flow Phase 4 分类为 `create_intent`，Phase 5 Action E 写入时自动将类型设为 `rest_day`。

### Cron 行为

纯休息模式 Cron 节点数相同（4 个），但内容切除所有任务安排：

```
10:00 — 晨间轻量问候
        「早安。今天去南京，玩得开心！🎒」
        + 日程事件主动提醒：
        「对了，你 9:45 的高铁别忘了～」

14:30 — 纯陪伴，不追问
        「在南京了吧？有什么新发现吗？」
        若有日程事件发生中 → 记录到 daily

17:30 — 事件收尾
        若有未发生的日程事件 → 提醒
        「今天过得怎么样？有遇到什么有趣的事吗？」

22:30 — 轻量复盘
        记录今日亮点
        次日预览
```

### 不能关闭的功能

即使在纯休息模式，以下照常执行：

- **日程事件提醒** — 高铁、航班、约会时间到了依旧提醒
- **体验记录** — 每日 memory/daily/ 依旧写入
- **收件箱检查** — 用户可能发了邮件要求调整计划

## `rest_day` 数据存储

### 存储位置

`rest_day` 声明存入 `planning/commitments.md`，与普通承诺共用同一张表：

```markdown
| # | 类型 | 承诺 | 目标日期 | 父承诺 | 来源对话 | 前置检查 | 提醒时间 | 状态 |
|---|------|------|---------|--------|---------|---------|---------|------|
| 1 | plan | 看《奥本海默》 | 2026-08-02 | - | 2026-07-29 邮件 | 买票 | morning | pending |
| 2 | rest_day | 南京旅游（全天外出） | 2026-08-08 | - | 2026-07-30 邮件 | - | - | pending |
```

字段变更：

- **新增 `类型`** — `plan`（普通承诺）、`rest_day`（全天休息声明）、`goal`（长期目标）、`step`（目标拆解步骤）
- **新增 `父承诺`** — 建立 goal → step 层级关系，`-` 表示无父级

### 检测逻辑

每个 Cron 节点 CHECK 阶段：

```text
1. 读取 commitments.md
2. 筛选：目标日期 == today AND 类型 == "rest_day" AND 状态 == "pending"
3. 若命中 → 今日切换为纯休息模式
4. 若未命中 → 按日历类型的默认模式执行
```

### 事后归档

rest_day 记录目标日期过后，跟随正常归档流程移到「已完成/取消」区域，14 天后自动归档到 `commitments-archive.md`。

## 长期目标的休息日任务拆解

### 数据模型

当用户表达长期意图时（如「下个月开始备考公务员」），Agent 在对话中帮助拆解为 goal + step 层级：

```markdown
| # | 类型 | 承诺 | 目标日期 | 父承诺 | 前置检查 | 提醒时间 | 状态 |
|---|------|------|---------|--------|---------|---------|------|
| 1 | goal | 备考公务员 | 2026-09-15 | - | 确认报名时间 | morning | pending |
| 1.1 | step | 买教材+参考资料 | 2026-08-02 | #1 | - | morning | pending |
| 1.2 | step | 每天刷 30 道行测题 | 每日 | #1 | - | all | pending |
| 1.3 | step | 整理申论素材 | 2026-08-10 | #1 | - | morning | pending |
```

**`#` 编号规则**：goal 用整数，其 step 用 `{goal号}.{序号}`，父子关系可读。

**目标日期为「每日」**：该 step 每天都出现在提醒列表中——但用户可以每天说不做，不影响明天继续尝试。

### 休息日自动提醒生成

Cron 10:00 CHECK 阶段：

```text
1. 读取 commitments.md 活跃行
2. 筛选逻辑：
   a. 目标日期 == today 的 step → 今日直接提醒（如「今天该买教材了」）
   b. 目标日期 == "每日" 的 step → 每日都提醒
   c. 目标日期在未来 7 天内的 step → 预览性提及
3. 组装邮件：
   - 先列今日到期的 step
   - 再列每日习惯类 step
   - 最后轻量提及未来一周的里程碑

用户可回复：
  「今天不想刷题，休息一天」 → 跳过今天，明天继续提醒
  「这周都不想搞副业」 → 相关 step 标记为 suspended，下次 Cron 询问是否恢复
```

核心原则：**只提醒，不强迫**。用户说不做，Agent 记录并调整，不做道德评判。

## 自动归档规则

### 规则

添加到 `commitments.md` Agent 操作指南：

1. **日常清理**（每个 Cron 节点 CHECK 前）：
   - 将「已完成/取消」区域中超过 14 天的记录自动移到 `planning/commitments-archive.md`
   - 归档文件按月份分组（`## YYYY-MM`）

2. **过期清理**（每日 22:30 节点）：
   - 扫描活跃承诺：目标日期超过 30 天且状态仍为 `pending` 的记录
   - 在邮件中轻量确认一次：「__ 的目标日期已经过了，是延期还是取消？」
   - 若用户 3 天内未回复 → 自动标记 `cancelled`，进入归档流程

3. **容量目标**：确保活跃行 ≤ 20 行，避免上下文膨胀。

### 归档文件结构

`planning/commitments-archive.md`：

```markdown
# 承诺归档

## 2026-08
| # | 承诺 | 目标日期 | 结果 | 归档日期 |
|---|------|---------|------|---------|
| 3 | 周末去爬山 | 2026-08-02 | 完成 | 2026-08-03 |

## 2026-07
| # | 承诺 | 目标日期 | 结果 | 归档日期 |
|---|------|---------|------|---------|
| 1 | 报名那个课程 | 2026-07-25 | 取消——用户决定不报了 | 2026-07-26 |
```

## 待确认的边界情况

1. 元旦/春节等长假期：用户可能连续声明多个 `rest_day`（如「初一到初五都在老家」）。Agent 应支持一条 `rest_day` 覆盖日期范围。
2. 半天休息 vs 全天休息：用户可能说「上午去医院，下午可以工作」——当前方案只支持全天声明。是否需要在 v1 就支持半天？
3. `rest_day` 覆盖工作日后，调休补班的逻辑是否需要特殊处理？（例如国庆调休补班日，用户请了年假）
