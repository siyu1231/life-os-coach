## 1. 项目概述

### 1.1 定位

Life Coach Agent 是一套**工具无关的 AI Skill Pack**，融合了 life-coach（小芽）的教练对话能力和 LifeOS 的系统化管理思想，通过 **Cron 定时触发 + 邮件主动触达** 驱动，形成一个会主动关心用户、推动进展、收集反馈、持续积累记忆的 AI 人生教练系统。

### 1.2 核心差异化

| 特性 | life-coach（小芽） | LifeOS | **本项目** |
|------|-------------------|--------|-----------|
| 教练能力 | ✅ 7 skill + ACT | ❌ | ✅ 完整继承 |
| 系统化管理 | ❌ | ✅ ISA/TELOS/Algorithm | ✅ 融合为 system 层 |
| 主动触达 | ❌ | ❌ | ✅ Cron + 邮件 |
| 邮件回复处理 | ❌ | ❌ | ✅ 轮询 + 状态机 |
| 工作日/假期感知 | ❌ | ❌ | ✅ 节假日 API |
| 滴答清单集成 | 提及但未实现 | ❌ | ✅ MCP 双通道 |
| 结构化记忆 | Markdown 模板 | 自动化 typed-item | ✅ 继承 life-coach 模板 + Tier 安全写入 |

### 1.3 设计原则

1. **工具无关**：不绑定特定 AI 编码工具。Cron 配置、邮件调用、MCP 接入均由 AI 工具根据协议文档自行实现
2. **渐进式复杂度**：用户刚开始只需最少的配置文件，随着使用深入自然扩展
3. **降级不中断**：外部工具不可用时自动降级到本地 Markdown，永远不阻塞主流程
4. **先少后多**：记忆从少量核心文件开始，只有内容持续增长才拆分
5. **写入前确认**：敏感信息写入前必须确认；日常状态更新可直接写入
6. **具身实践边界**：AI 是做镜子、脚手架、记录员和项目经理，不能替代真实练习

## 3. Engine 引擎层

### 3.1 `cron-system.md` — 定时规则

#### 3.1.1 时间点定义

| 时间点 | 运行条件 | 名称 | 触发动作 |
|--------|----------|------|----------|
| `09:30` | 仅工作日 | 晨间启动 | 读今日计划 → 发邮件告知今日任务 + 询问今日意图 |
| `10:30` | 仅工作日 | 第一时段检查 | 问进度 + 接收回复 → 调整计划 |
| `14:30` | 仅工作日 | 下午第一次 | 同上 + 附带上午完成率反馈 |
| `15:30` | 仅工作日 | 下午第二次 | 同上 |
| `16:30` | 仅工作日 | 下午第三次 | 同上 |
| `17:30` | 仅工作日 | 日间收尾 | 全天汇总 → 未完成项处置 → 收尾提醒 |
| `22:30` | 每日 | 晚间复盘 | 工作日：复盘当天执行 / 假期：轻松回顾 |
| 发送后+5min | 动态 | 回复轮询1 | 查是否有新回复 → 有则处理 |
| 发送后+10min | 动态 | 回复轮询2 | 再次检查 → 有则处理，无则会话关闭 |

#### 3.1.2 假期模式

**工作日判断**：调用 `https://timor.tech/api/holiday/info/{date}`

- `type.type === 0` 且 `holiday === null` → 工作日
- `type.type !== 0` 或 `holiday !== null` → 休息日

备份 API：`https://www.mxnzp.com/api/holiday/single/{date}`（需要注册获取 app_id/app_secret）

**假期行为**：
- 日间检查点全部跳过
- `09:30` 可选发送简短问候
- 晚间复盘切换轻量模式："今天发生了什么开心的事？"

#### 3.1.3 参数化

用户在首次配置时可以：
- 调整各时间点
- 选择启用/禁用特定时间点
- 自定义每个时间点的询问风格

### 3.2 `email-protocol.md` — 邮件协议

#### 3.2.1 发送邮件

使用腾讯企微 API `POST /cgi-bin/exmail/app/compose_send`：

- 收件人、标题、正文（支持 HTML）
- 附件加正文不超过 50M

**邮件正文模板结构**：
```
[时间点卡片：如 🕙 10:30 时段检查]

[上下文简述：上一时段完成情况 + 当前剩余任务]

[具体问题：1-2 个，可选项优先]

[行动提示：回复此邮件即可]
```

#### 3.2.2 接收邮件

采用「发送后轮询」模式（企微回调只推送数量，不含正文）：

1. 发送邮件后，设置 5min 和 10min 两个回复轮询 cron
2. 轮询时调用企微 API 获取收件箱新邮件列表
3. 筛选发件人为用户的邮件
4. 获取邮件正文 → 解析自然语言回复
5. 一次会话只处理第一封有效回复

#### 3.2.3 查询应用邮箱地址

`POST /cgi-bin/exmail/app/get_email_alias` → 获取主邮箱和别名

### 3.3 `session-flow.md` — 会话状态机

```
[Cron 触发]
     │
     ├── 1. 前置检查：调用节假日 API → 判断运行条件
     │
     ▼
[Phase 1: 采集] ─ 读记忆 + 滴答/本地计划 → 了解 Current State
     │
     ▼
[Phase 2: 触达] ─ 组装邮件并发送
     │
     ├── 设置 5min / 10min 回复轮询 cron
     │
     ▼
[Phase 3: 接收] ─ 轮询收件箱，找到用户回复
     │
     ├── 无回复 → 本次结束
     │
     ▼
[Phase 4: 理解] ─ 解析回复内容
     │   ├── 纯状态更新 → 更新计划
     │   ├── 情绪/困难信号 → 路由到 coach 层
     │   ├── 修改请求 → 调整计划
     │   └── 深度问题 → 引导到 CLI/Chat
     │
     ▼
[Phase 5: 行动] ─ 执行变更
     │   ├── 更新滴答/本地计划
     │   ├── 写入 memory
     │   └── 必要时调用 coach skill
     │
     ▼
[Phase 6: 闭环] ─ 发送确认邮件
     │   ├── 概述已做的更新
     │   └── 告知下次检查时间
     │
     ▼
[结束本次会话]
```

## 4. System 系统层

### 4.1 `algorithm.md` — 统一执行循环

```
CHECK ─→ GAP ─→ DECIDE ─→ ACT ─→ VERIFY ─→ LEARN
  │        │        │        │        │         │
  │        │        │        │        │   本次有什么值得
  │        │        │        │   工具确认    记住的？
  │        │        │   发邮件/写文件     │
  │        │   纯状态同步？       │         │
  │    计划 vs 实际   需要coach？     │         │
  │    的差距        需要改计划？     │         │
读记忆    用户状态      到复盘时间？     │         │
+ 计划    信号                     └─────────┘
```

### 4.2 `isa-system.md` — ISA 格式与规则

任何大于「看一眼就能回答」的目标，先写下 ISA：

```markdown
# ISA：<目标名称>
## Goal（用户原话）
## Vision（这背后的意图是什么）
## Out of Scope（不做什么）
## Claims（可验证的声明）
  - [ ] 声明内容 → 验证方式
## Anti-claims（不希望发生的事）
```

Coach 场景中的 ISA 不需要代码级严格性，但保留核心精神：**「做完」有标准，不是感觉**。

### 4.3 `memory-system.md` — 结构化记忆

#### 4.3.1 目录结构

```
life-coach-data/
├── profile/
│   ├── user.md           # 稳定底图：作息、偏好、精力线索
│   └── life-compass.md   # 愿景、价值、阶段主题（= LifeOS TELOS）
├── planning/
│   ├── weekly-plan.md
│   └── daily-plan.md
├── projects/
│   └── projects.md
├── reviews/
│   └── review-log.md
├── habits/
│   └── habit-tracker.md
└── memory/
    ├── daily/YYYY-MM-DD.md
    └── long-term.md
```

#### 4.3.2 四级写入安全

| Tier | 写入类型 | 确认要求 |
|------|---------|---------|
| A | 用户刚确认的计划、今天实际记录 | 直接写入 |
| B | 精力线索、启动阻力、有效策略（重复出现后） | 写入前告知 |
| C | 价值观、身份描述、人生方向 | 需先确认 |
| D | 不记录：心理诊断、敏感情感宣泄、密码密钥 | 永远不写 |

#### 4.3.3 核心原则

1. **先少后多**：从核心文件开始，内容增长再拆分
2. **单一事实源**：同一条信息只在一个文件维护
3. **先记录再提炼**：单次观察放 daily，多次出现再沉淀为长期规律
4. **事实、假设、洞察分开**：事实是用户说的，假设标注「暂时假设」，洞察是对话确认的理解
5. **memory/ 不是另一套 profile**：long-term.md 只放跨文件洞察和索引

### 4.4 `telos-system.md` — 愿景模型

统一管理「我是谁、我要去哪、什么重要」，融合 life-coach 的人生 8+1 平衡轮和 LifeOS 的结构化 TELOS。

### 4.5 `verification.md` — 验证规则

| 级别 | 标准 | 示例 |
|------|------|------|
| **数据验证** | 数字/文件/时间戳 | "任务完成率 60%"（滴答显示 3/5） |
| **证据验证** | 有具体事实支持 | "这周三次拖延，分别在周二、周三、周五" |
| **觉察验证** | 用户明确表达的感受 | "你说这周很累，尤其是下午" |

原则：「数据优先，感觉补充，两者合起来才是完整的当前状态」。

## 5. Coach 教练层

### 5.1 `coaching-process.md` — 共享教练流程

life-coach 原版 7 步完整保留：建立安全 → 接住情绪 → 澄清主题 → 促进觉察 → 聚焦选择 → 共创行动 → 整合收尾。

**新增：邮件场景的对话约束**：

- 每封邮件一个核心问题，用户可一句话回复
- 分析不超过 200 字
- 给选项优于开放式提问
- 需要深度对话的话题引导到 CLI/Chat

### 5.2 `act-core.md` — ACT 底层

完整保留 life-coach 的 ACT 六大过程。**新增：邮件场景的微干预速查表**，覆盖「状态不好」「不想做」「我不行」「明天再说」四种高频邮件回复。

### 5.3 七个 Coach Skills

每个 skill 包含：`SKILL.md` + `mail-trigger.md` + `references/`。

| Skill | 邮件触发信号 | 触发后动作 |
|-------|-------------|-----------|
| **life-vision** | 迷茫、方向感缺失、多次计划偏离非执行问题 | 引导到 CLI/Chat |
| **planning** | 每日启动 + 改计划 + 收尾处置 | 调整滴答/本地计划 |
| **procrastination-execution** | 连续2时段未推进、"不想做"、"没动力" | 压缩任务 → 微启动 |
| **review** | 晚间复盘、用户说"这周又废了" | 结构化复盘 → 提炼 |
| **habit-design** | 同一偏离反复出现 | 微习惯设计 |
| **energy-management** | "累"、"困"、低完成率 | 精力审计 + 重排 |
| **complex-problem-solving** | 多因素纠缠、问题定义不清 | 引导到 CLI/Chat |

### 5.4 跨 Skill 转交规则

继承 life-coach 原版的转交规则：
- planning 中发现无方向 → 转 life-vision
- planning/execution 中发现耗竭 → 转 energy-management
- procrastination 中发现需要长期重复 → 转 habit-design
- review 中发现复杂纠缠 → 转 complex-problem-solving

## 6. Integrations 集成适配层

### 6.1 `dida-mcp.md` — 滴答清单

#### 6.1.1 能力映射

| 操作 | MCP 调用 | 降级（MCP 不可用） |
|------|---------|-------------------|
| 读今日任务 | `get_tasks(filter: today)` | `planning/daily-plan.md` |
| 读项目列表 | `get_projects()` | `projects/projects.md` |
| 创建任务 | `create_task(...)` | 追加到 daily-plan.md |
| 更新任务状态 | `update_task(id, status)` | 编辑 Markdown |
| 改截止时间 | `update_task(id, due)` | 编辑 Markdown |

#### 6.1.2 降级策略

```
每个滴答操作：
  1. MCP 连接可用？→ 走 MCP
  2. 不可用 → 走本地 Markdown + [待同步到滴答] 标记
  3. MCP 恢复后 → 询问是否批量同步
```

#### 6.1.3 数据原则

- **滴答是任务执行的主记录**
- **本地 Markdown 是镜像和兜底**
- **愿景/项目/复盘始终走本地**：滴答只管任务执行
- **不双写**：MCP 可用时不写 Markdown 任务

### 6.2 `tools.md` — 通用接入规则

```
1. 读取更主动，写入更谨慎
2. 外部工具不可用 → 降级到本地 Markdown
3. 写入外部工具前先确认（创建/修改/删除）
4. 新工具接入：用户提供配置 → 参考文档 → 记录到此文件
```

## 7. 交互模式

### 7.1 邮件交互（日常）

- 定时 cron 触发 → 发邮件询问 → 用户回复 → 处理 → 发确认
- 适用于：状态采集、计划调整、复盘问答
- 最大回复延迟：发送后 10 分钟（两次轮询后关闭）

### 7.2 CLI/Chat 交互（深度）

- 用户在 AI 工具中直接对话
- 适用于：人生愿景澄清、复杂问题分析、深度教练对话
- 邮件中发现需要深度对话的信号时，引导用户打开 Chat

### 7.3 交互选择规则

```
用户输入性质：
├── 状态更新、任务调整、简短确认 → 邮件
├── 方向迷茫、复杂决策、情绪需要承接 → 引导到 Chat
├── 用户自己主动开 Chat → 深度对话模式
└── Chat 中达成结论 → 行动项写回邮件提醒系统
```

## 8. 首次安装流程

1. 用户将项目 clone 到本地或直接给 AI 工具使用
2. AI 工具读取 `AGENTS.md` 了解整体架构
3. AI 工具读取 `engine/cron-system.md`，询问用户：
   - 确认/调整时间点
   - 确认工作日范围
   - 配置 Cron（AI 工具自行完成）
4. AI 工具读取 `engine/email-protocol.md`：
   - 确认企微应用已配置
   - 获取 access_token
   - 查询应用邮箱地址
5. AI 工具读取 `templates/`，帮助用户创建初始用户数据：
   - `profile/user.md`（基本作息和偏好）
   - `profile/life-compass.md`（初步方向）
6. 如果检测到滴答 MCP → 读取 `integrations/dida-mcp.md` 并接入
7. 发送第一封启动邮件：「你好，我是你的 AI 人生教练。从明天 9:30 开始，我会定期陪你推进每一天。」

## 10. 安全边界

- 本系统是人生教练和自我管理辅助，不是心理治疗、医疗诊断、法律或财务建议
- 自杀/自伤/危机信号 → 优先安全处理，建议联系专业人士
- 严重持续的心理症状 → 建议寻求专业支持
- 重大不可逆决定 → 只帮助澄清价值和选项，不替代决策
- 不把所有痛苦解释成「需要计划」或「需要行动」
