# 拖延应对邮件交互示例

本示例展示 Life Coach Agent 在检测到用户连续未推进任务后，通过邮件进行拖延应对的完整交互回合：Cron 触发 -> 拖延检测 -> 邮件发送 -> 用户回复 -> Agent 处理 -> 确认邮件 -> 文件变更前后对比。

## 场景设定

- 用户：小张，产品经理
- 日期：2026-07-29（周三，工作日）
- 触发时间点：15:30（Fixed Cron，下午中段状态检查）
- 背景：用户早上承诺在上午完成原型修改（见 `morning-checkin.example.md`），但 10:30 和 14:30 两次状态检查均显示该任务未推进
- 通道：企微邮件

## 交互回合

### Phase 1: 采集（Gather）

```
[Cron 15:30 触发]
  -> getDayType("2026-07-29") => "workday"
  -> 读取 profile/user.md：
     - 用户常见拖延原因：完美主义、任务太大不知从何下手、怕改了又要改
     - 有效启动方式：先画草稿不追求完美、25 分钟番茄钟、把"改好"改成"改一版出来"
     - 下午容易走神，15:00 后精力下降
  -> 读取 memory/daily/2026-07-29.md：
     - 09:30 用户设定今日核心任务：原型修改
     - 10:30 状态检查：用户回复"还在搞，有点卡"
     - 14:30 状态检查：用户未回复
  -> 拖延信号检测：
     - 同一任务（原型修改）连续 2 个时段（10:30 + 14:30）未推进或卡住
     - 匹配 procrastination-execution 的 trigger: "连续 2 个时段同一任务未推进"
  -> 发送决策：正常发送，使用 procrastination-execution 模板
```

### Phase 2: 触达（Reach）

**Agent 发送的邮件：**

```
主题：原型修改卡住了？没什么大不了的

小张，下午好。

你早上说要收掉原型，但这会儿卡住了是吧。这很正常——想改好就容易卡。

先不想"改好"，想一个更小的事：接下来 25 分钟，你能对原型做的**最小的一个改动**是什么？
A. 打开文件看一眼现在长什么样
B. 改一个按钮的位置或文案
C. 画一个你想要的布局草图（不管美丑）

选一个，25 分钟后告诉我就行。
```

### Phase 3: 接收（Receive）

**用户回复（邮件内容）：**

```
唉，一直在改同一个页面，改了 5 版都不满意，越改越丑。想推倒重来又觉得时间不够。
```

**Agent 解析：**
- `mailid`: msg_20260729_153701_d4e8
- `reply_to_mailid`: msg_20260729_153000_c9f1（Agent 发送的邮件）
- `content_classification`: `procrastination_perfectionism`（完美主义拖延）
- 拖延类型识别：
  - 完美主义拖延（"改了 5 版都不满意"）
  - 过度投入导致边际收益递减（"越改越丑"）
  - 推倒重来的冲动（"想推倒重来"）vs 时间约束（"时间不够"）

### Phase 4: 理解（Interpret）

```
[理解阶段]
  -> 用户处于典型的"完美主义-反复修改-不满-想重来"循环
  -> 分类：perfectionism_spiral（完美主义螺旋）
  -> 路由到 procrastination-execution skill
  -> 判断：邮件可以处理，暂不需要切换到 CLI/Chat（用户尚未出现强烈情绪，属于可轻量干预阶段）
  -> 需读取 procrastination-execution 的 workflow.md 中完美主义拖延应对方法
```

### Phase 5: 行动（Act）

**Agent 执行以下操作：**

1. 读取 `procrastination-execution/references/procrastination-toolkit.md` 中完美主义应对章节
2. 更新 `memory/daily/2026-07-29.md`，记录拖延信号和干预
3. 更新 `profile/user.md` 执行线索（如发现新拖延模式）
4. 生成确认邮件

**文件变更前后对比：**

`memory/daily/2026-07-29.md` 新增内容：

```markdown
## 15:30 拖延干预

- cron_slot: mid_afternoon
- channel: email
- 用户回复时间: 15:37
- 拖延类型: 完美主义螺旋（反复修改 5 版仍不满意）
- 用户原话: "改了 5 版都不满意，越改越丑。想推倒重来又觉得时间不够。"
- 干预方式: 暂停修改，先定义"最低可接受版本"
- 识别信号: 过度修改导致边际收益递减，推倒重来的冲动是完美主义的另一种表现（换一张白纸重新追求完美）
- 备注: 用户对"视觉美感"有较高要求，这既是优势（产出质量高）也是常见卡点
```

`profile/user.md` 执行与拖延线索部分变更前：

```markdown
## 执行与拖延线索

- 常见启动阻力：任务太大、不知从何下手
- 常见触发场景：需要"写文档"、"出方案"时出现
- 有效启动方式：先画草稿不追求完美、25 分钟番茄钟
- 容易反效果的方式：被催、给 deadline 压力
```

变更后（新增一条）：

```markdown
## 执行与拖延线索

- 常见启动阻力：任务太大、不知从何下手、视觉/美感要求高导致反复修改
- 常见触发场景：需要"写文档"、"出方案"时出现；涉及 UI/视觉呈现的任务尤甚
- 有效启动方式：先画草稿不追求完美、25 分钟番茄钟、先定义"最低可接受版本"再开始
- 容易反效果的方式：被催、给 deadline 压力
- 拖延模式（2026-07-29 观察到）：完美主义螺旋——已投入多版修改 -> 边际收益递减 -> 不满积累 -> 想推倒重来 -> 但时间不够 -> 卡住
```

### Phase 6: 闭环（Close）

**Agent 发送确认邮件：**

```
主题：别推倒重来，先定一个"能交差"的版本

小张，收到。

改了 5 版说明你在乎这个原型。但第 5 版一定比第 1 版好——只是你的眼睛已经看麻了。

先不要推倒重来。做一件事：定义"今天能交差的最低版本"——比如只需要 3 个核心页面、交互跑通、视觉不丑就行。

剩下的精致化，留给明天。

今天收工前（17:30）我会再问你一次进度。不着急，慢慢来。

——小芽
```

## 拖延应对的关键设计原则

1. **不道德评判**：不把拖延等同于"懒""意志力差"，而是看作任务难度、情绪阻抗和精力约束共同作用的结果。
2. **信号而非缺陷**：拖延是一种信号，告诉用户（和 Agent）"这件事的启动阻力超过了当前可调动的资源"。
3. **降低门槛优先于分析原因**：先帮助用户迈出最小一步，而不是分析完所有原因再行动。
4. **小实验替代宏大承诺**：用"25 分钟只做一个改动"替代"今天必须完成原型"。
5. **渐进式画像**：单次拖延不写成长期规律；多次出现后才沉淀到 profile/user.md。

## 这个示例展示的能力

- 拖延信号自动检测：同一任务连续 2 个时段未推进 -> 触发 procrastination-execution
- 拖延类型识别：从用户回复中识别"完美主义螺旋"
- 不追问不催促：邮件聚焦"接下来 25 分钟的最小一步"，不追问"为什么还没做完"
- 画像持续更新：将新的拖延模式记录到 profile/user.md 执行线索中
- 与后续 Cron 节点的衔接：确认邮件预告 17:30 会再问进度，保持陪伴感
