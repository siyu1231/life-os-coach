# 工具适配层

> 定义 Agent 接入外部工具的统一原则、降级规则、写入确认规则和扩展流程。所有外部集成（滴答 MCP、日历 API、Notion、Obsidian 等）均遵循本文件定义的规范。

## 一、接入原则

### 1.1 读取更主动，写入更谨慎

| 操作类型 | 态度 | 说明 |
|---------|------|------|
| 读取 | 主动 | 在 CHECK 阶段主动拉取工具数据以了解用户状态，无需每步询问用户 |
| 写入 | 谨慎 | 创建、修改、删除外部数据前必须获得用户明确确认 |

**读取主动性的边界**：
- 每次主动读取仅限于当前循环（CHECK 阶段）需要的数据，不做全量拉取。
- 同一工具在同一 CHECK 阶段不重复读取相同数据（除非数据可能已过时，如等待一段时间后重试）。
- 读取不要求用户事先许可，但读取失败时告知用户并降级。

**写入谨慎性的边界**：
- 写入操作限于 DECIDE 阶段决定的动作，不在 CHECK、GAP 或 VERIFY 阶段写入。
- 写入前需要用户确认，确认形式为用户自然语言回复中的明确表态。
- 批量写入（如从滴答迁移到另一个工具）需要用户逐项或整体确认。
- 高风险操作（删除、批量修改）需要用户额外确认意图。

### 1.2 工具无关，数据为本

Agent 的核心能力是对用户状态的理解和教练对话，不绑定到任何特定工具。工具是可替换的接口层：

```
用户需求 → 能力抽象 → 工具适配层 → 具体工具实现
                │               │
                └───────────────┘
                    降级路径
```

如果滴答换成 Todoist，只需要更换适配层的具体实现；Agent 的推理、计划、教练能力不受影响。

### 1.3 一个事实源，不维护副本

每类数据只有一个事实源（source of truth）：

| 数据类型 | 默认事实源 | 降级事实源 |
|---------|-----------|-----------|
| 任务状态 | 滴答清单（MCP 可用时） | 本地 Markdown |
| 日程事件 | 日历 API（MCP 可用时） | 本地计划文件 |
| 用户画像 | `profile/user.md` | 无降级（本机文件） |
| 记忆与洞察 | `memory/` 目录 | 无降级（本机文件） |
| 计划与项目 | `planning/` + `projects/` | 外部工具降级后仍以本地为主 |

### 1.4 声明以工具证据关闭

派生自 `system/algorithm.md` 核心原则「没有证据 = 没做完」。所有关于外部数据的声明（「任务已创建」「邮件已发送」「日历已更新」）必须附带对应的工具验证：

- 创建 → 读取确认存在。
- 修改 → 读取确认字段已变更。
- 删除 → 读取确认不存在或状态已变更。
- 发送 → 读取确认已发送且有唯一标识。

## 二、降级不中断

### 核心原则

**外部工具不可用 → 降级到本地 Markdown，不阻塞教练过程**。

### 降级通用规则

1. **无中断**：工具调用失败时，Agent 不卡住，立即切换到降级路径。
2. **有标记**：降级输出的内容添加统一标记，表明当前数据非来自事实源。
3. **可恢复**：标记格式统一，方便工具恢复后通过自动化或人工操作进行同步。
4. **不重试**：连续 2 次调用失败后即降级，不在单次交互中反复重试。

### 降级标记规范

| 场景 | 标记 | 示例 |
|------|------|------|
| 工具完全不可用 | `[工具名 离线]` | `[滴答 离线]` |
| 单条数据写入但未同步 | `[待同步到 工具名]` | `[待同步到 滴答]` |
| 读取降级 | 在本地数据来源旁标注 `[非实时]` | `[非实时] 来自本地计划文件` |

### 恢复后流程

1. Agent 在后续 CHECK 阶段检测到工具恢复。
2. 不主动执行批量同步（避免未经确认的数据操作）。
3. 在合适的交互窗口（每日早安、计划调整、用户主动发起）以向用户提问的方式告知：「XX 工具已重新连接。本地有 N 条标记为 `待同步` 的数据，是否现在同步？」
4. 用户确认后，逐条同步，完成后移除待同步标记。

## 三、写入前确认规则

### 需要确认的场景

| 场景 | 确认要求 | 示例 |
|------|---------|------|
| 创建外部数据 | 用户明确说出要创建的意图 | 「帮我把'买牛奶'加到待办」→ 确认 → 创建 |
| 修改外部数据 | 用户指定修改内容和目标值 | 「把截止改到周五」→ 确认 → 更新 |
| 删除外部数据 | 用户使用「删除」「移除」等同义关键词 | 「删掉那个过期任务」→ 再次确认 → 删除 |
| 批量操作 | 用户明确要求批量处理，或逐条确认 | 「把今天完成的全标记了」→ 用户确认每个或整体 |
| 本地文件写入（profile/长期记忆） | 用户确认或 Agent 总结后用户认可 | 「我们是不是决定优先 xx？」→ 用户确认 → 写入 |

### 不需要确认的场景

| 场景 | 理由 |
|------|------|
| 读取外部数据 | 读取是了解用户状态的必要步骤，不影响数据 |
| 写入 memory/daily 的事实记录 | 当天的行为记录是事实性数据，非推断性内容 |
| 写入系统日志/游标状态 | 系统内部状态维护，不涉及用户数据 |
| 用户明确授权的自动操作 | 如用户之前说过「以后早上的待办直接帮我标完成」 |

### 确认的粒度

| 操作类型 | 建议的确认粒度 |
|---------|--------------|
| 创建单条任务 | 一句自然语言确认即可 |
| 修改任务字段 | 指出修改对象和字段值的句子 |
| 删除任务 | 明确提及「删除」的句子 |
| 批量创建（3 条以下） | 在回复中列出所有任务，用户一次性确认 |
| 批量操作（3 条以上） | 先询问用户是否需要此批量操作，用户确认后开始逐条或列表式执行 |

## 四、新工具扩展流程

### 扩展流程

```
用户提供工具信息 ──→ 记录到本文件 ──→ Agent 读取生效
```

### 具体步骤

**Step 1：用户提供信息**

用户以自然语言提供新工具的信息，例如：
- 「我用了 Notion 管理项目，API key 是 xxx。」
- 「帮我接上我的 Google Calendar。」
- 「我改用 Todoist 了，这是 token。」

**Step 2：Agent 确认并记录**

Agent 应主动询问并记录以下关键信息：

```markdown
## {工具名称}

- 工具类型：{待办 / 日历 / 笔记 / 习惯 / 其他}
- 接入方式：{MCP / REST API / 本地文件}
- 事实源数据类型：{任务 / 日程 / 笔记 / ...}
- 接入凭据：{API Key / Token / 配置路径}（不写入版本控制）
- 能力范围：{可读 / 可写 / 可删除 / 可查询}
- 优先级：{主要工具 / 辅助工具 / 备用工具}
- 备注：{用户提供的额外约束或偏好}
```

**Step 3：Agent 接入**

1. 根据工具类型匹配合适的能力抽象层（待办能力、日历能力、笔记能力等）。
2. 验证接入凭证的有效性（如调用一次只读 API 测试连通性）。
3. 在 CHECK 阶段将该工具纳入数据源。
4. 在后续交互中按本文件的访问和写入规则操作。

**Step 4：退出或更换**

用户更换工具时的处理方式：

1. 确认旧工具的数据迁移需求：「旧工具上的现有数据需要迁移吗？」
2. 用户确认后，协助迁移（前提是旧工具和新工具均可用）。
3. 更新本文件的工具配置。
4. 清理旧工具的凭据引用。

### 不支持的场景

- Agent 不接受通过自然语言分享的第三方服务密码（密码只能通过安全渠道配置）。
- Agent 不自动安装未在环境中配置的 MCP 服务（需要用户通过 Claude Code settings 配置）。
- Agent 不接入用户未明确授权的工具。

## 五、未来可扩展工具类型

### 5.1 日历 MCP

| 能力 | MCP 调用示例 | 降级路径 |
|------|------------|---------|
| 读取当日日程 | `get_today_events` | 读取 `planning/daily-plan.md` 中的日程规划 |
| 读取某日日程 | `get_events_by_date` | 读取对应日期的计划文件和 memory |
| 创建事件 | `create_event` | 本地 Markdown 标注 `[待同步到日历]` |
| 更新事件 | `update_event` | 本地 Markdown 记录变更 |
| 查询忙闲 | `get_free_busy` | 询问用户当前时段是否可用 |
| 删除事件 | `delete_event` | 本地 Markdown 标注 `[待同步到日历]` |

**集成要点**：
- 日历数据对计划 skill（planning）和每日 CHECK 很重要，应优先接入。
- 日历读取应在每日早安节点自动执行（读取当日日程），无需用户确认。
- 日历写入（创建/修改事件）必须用户确认。
- 日历和滴答共享「不双写」原则：MCP 可用时不将日程复制到本地计划文件。

### 5.2 Notion API

| 能力 | 适合的场景 | 降级路径 |
|------|-----------|---------|
| 读取项目文档 | 项目复盘、背景调查 | 本地 `projects/` 目录 |
| 写入复盘记录 | 用户要求将复盘同时保存到 Notion | 本地 `reviews/` 目录 |
| 更新项目状态 | 项目进展同步 | 本地项目文件 |
| 查询数据库 | 任务或目标列表 | 本地 `planning/` 或 `projects/` |

**集成要点**：
- Notion 适合作为知识库和项目背景的事实源。
- Notion 写入操作需要用户明确确认，尤其是涉及已有文档结构的修改。
- 不自动用 Notion 数据覆盖本地文件，反之亦然（除非用户要求）。
- Notion 的数据（项目背景、笔记）与滴答的数据（任务状态）不重叠，因此不存在双写冲突。

### 5.3 Obsidian

| 能力 | 适合的场景 | 降级路径 |
|------|-----------|---------|
| 读取笔记 | 用户日记、周记、项目笔记 | 本地 `_reference/` 或 `memory/` |
| 写入笔记 | 复盘、洞察 | 本地文件直接写入（Obsidian 本身就是本地文件） |
| 搜索笔记 | 查找历史信息 | 本地文件搜索 |

**集成要点**：
- Obsidian 是本地优先的工具，与本地 Markdown 文件天然兼容。
- 接入方式可以是直接读写本地 Obsidian vault 目录。
- 无需降级（因为本身就是本地文件）。
- 注意 Obsidian vault 路径与项目文件路径不冲突。

### 5.4 其他潜在工具类型

| 工具类型 | 用途 | 接入优先级 | 说明 |
|---------|------|-----------|------|
| 习惯追踪 App | 习惯完成数据读取 | 中 | 习惯设计 skill（habit-design）的直接数据源 |
| 时间追踪工具 | 时间使用分析 | 低 | 辅助精力管理 skill（energy-management） |
| 健身/健康 API | 运动、睡眠、心率数据 | 低 | 健康维度的数据补充 |
| 邮件/IM 工具 | 接收和回复用户消息 | 高 | 已在 `engine/email-protocol.md` 中定义 |
| Git 平台 | 项目进度和提交记录 | 低 | 仅适用于软件开发类用户的特定场景 |

### 5.5 新工具接入优先级参考

| 优先级 | 工具类型 | 理由 |
|-------|---------|------|
| P0 | 待办 MCP + 日历 MCP | 覆盖每日计划和调度的核心需求 |
| P1 | 笔记/知识库类（Notion/Obsidian） | 覆盖项目背景和复盘记录 |
| P2 | 习惯追踪、时间追踪 | 覆盖行为数据输入 |
| P3 | 健身、健康、Git 平台等 | 特定场景的增强数据 |
